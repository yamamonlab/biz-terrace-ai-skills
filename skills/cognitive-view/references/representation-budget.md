## なぜこのファイルがあるか

本 Skill の規定は **上限しか持っていなかった**（図は3枚まで、カードは4枚まで、node ≤9）。下限が無いので、**全部を箱に入れた箇条書きにしても満点が出る**。

実測された失敗はこれ。`examples/sample-document.md`（5,416字）を変換した出力は、情報保持率 100% / 表現変換率 100% で合格したが、描画すると:

- 構造層9ブロックのうち **図は1枚（≈11%）**、残りは箇条書きと表と散文
- **箇条書きが5ブロック** 並び、中盤以降が同じ見た目のテキスト塊の連続
- 1024px 幅で **3,028px（3.4画面）**

**表現変換率は「散文でない」を測っているだけで、「見て分かる」を測っていない。** 箇条書きは散文ではないが、位置や大小で情報をエンコードしていないので、読む負荷はほとんど下がらない。このファイルはその差を埋める。

**予算表は HTML を1行も書く前に作る。** 出した後の自己採点は、判断を出力に合わせて後付けできてしまう（3文テストが実際にそうなった。4節参照）。

## 1. 装置の3階層

| Tier | 装置 | 何でエンコードするか | 下限の分子に入るか |
|---|---|---|---|
| **A 図的** | 図（inline SVG）、timeline、棒、メーター | **位置・長さ・角度** | ✅ |
| **B 構造的** | 表、メトリクスカード群 | **行列位置**（表は1セル30字以内の時だけ） | ✅ |
| **C 強調のみ** | アラート枠、箇条書き、日付付きリスト | 面と順序 | ❌ |

**Tier B は条件付きである。** 表のセルが文になると、行列位置によるエンコーディングが効かなくなり「グリッドに入った散文」になる。**30字超のセルが全体の10%を超えた表は、Tier B に数えない**（`references/output-contract.md` のセル予算）。

**アラート枠と箇条書きは Tier C。** どちらも「目立たせる」「順番に並べる」だけで、量や関係をエンコードしていない。読む装置である。

## 2. 第1層 — リズム

- **同一装置を2つ連続させない。** 箇条書きの次は箇条書き以外を置く。置けないなら、それは1つの塊に統合できるということ
- **散文（`<p>`）は2つ以上連続させない。** 3つ目が要るなら §4 Visual Router で引き直す
- 問い見出し1本の下で、同じ装置が3回以上出たら、その見出しは論点が分かれていない

## 3. 第2層 — 視覚エンコーディングの下限

分母は表現変換率と同じ「関係を持つ塊」（`references/quality-rubric.md` 主指標2の手順で切る）。

| 指標 | 下限 |
|---|---|
| **Tier A（図的）** | **20% 以上** |
| **Tier A + B** | **50% 以上** |
| 関係塊が6つ以上ある場合 | **Tier A を2つ以上** |
| 読む系の**面積比**（散文 + 箇条書き + アラート枠 + 表のテキストセル） | **60% 以下** |

面積比は描画して測る（`references/output-contract.md` の自己レビュー節）。**個数だけだと、大きな表1つと小さな図1つが同点になる。**

**下限を満たせない時、装置を足して埋めてはいけない。** 数値のない資料にカードや棒を作る、関係のない列挙を表に入れる、装飾の図を描く——これは水増しであり、即 FAIL 2（原文にない情報の追加）に当たる。

満たせない時は次のどちらかを記録して進む。

1. **入力が本当に列挙中心** — 関係を持つ塊が3つ未満。予算表に「下限を適用せず。理由: 関係を持つ塊が N 件」と書く
2. **塊の切り方が細かすぎる、または型に到達していない** — 多くはこちら。特に**時系列を箇条書きへ落としていないか**を最初に疑う（§4の反転ルール）

関係を持つ塊が **3つ以上あるのに Tier A が0** なら、これは箱組みへの退行であり出荷しない（`quality-rubric.md` 即 FAIL 7）。

## 4. 第3層 — 図の事前散文

**図の候補は、必ず3系統から挙げる。** 支配的関係の図だけを検討して終わると、型が同梱されていても到達しない。

| 系統 | 何を描くか | 型 |
|---|---|---|
| **関係** | 依存・因果・対立・構造 | `type-flowchart` / `type-state` / `type-tree` / `type-quadrant` |
| **時間** | 経過・滞留・並行・順序 | `type-timeline` / `type-process` |
| **量** | 大小・比率・推移（原文に数値がある時のみ） | `type-bar` |

3候補それぞれに事前散文と文数を書き、採用したものと、しなかった理由を残す。**採用0でも候補の記録は残す**（次に同じ入力を見た時、検討済みだと分かる）。

量の図で原文に値が無い対象がある場合、**「原文に記述なし」を空スロットとして描くのは捏造ではない**。値を推定して埋めるのが捏造である。

**図を描くと決めたら、描く前にその図の内容を散文で予算表に書く。** 文数を数えて2文以下なら図にしない。

これは3文テストの運用規定である。自己申告のままだと、通したい図に合わせて文を割れてしまう。実例:

> 「営業部の2週間トライアルは3日で利用が9割落ちた。理由は出力が長すぎる・信頼できず原文を開き直すの2つで、結果として時間は減らなかった。」

これは **2文** なので図にしてはいけなかった。実際には3文に割られて図が通り、node 5 / edge 5 の直線フローが出力に残った。**散文を先に書いて予算表に置けば、この判断は後から検証できる。**

図が却下された時、その塊は表・箇条書きへ落とす。代わりに、**その資料の支配的関係**（`SKILL.md` §3）を表す図が描けないかを1度だけ問い直す。上の例では「3つの未確認前提が、それぞれ何をブロックしているか」が散文で3文を超え、comprehension_goal に直結していた。

## 5. ページ予算

- **5秒層と、最初の問い見出しの先頭が、1画面（縦 900px 相当）に入る**こと
- 超える場合、メトリクスカードを減らすのではなく、`<p class="note">` の説明文を削る
- ページ全長に上限は置かない（情報を保つ設計のため）。ただし予算表に実測値を記録し、前回より伸びた時は理由を書く

## 6. 予算表の書式

出力前に、この表を作ってから HTML を書く。提出は求めない（作業用）。

```yaml
input: sample-document.md / 5,416字 / 停滞検討
dominant_relation: 未確認の前提が比較の成立をブロックしている（依存）

blocks:
  - id: b1
    question: 今どこにいるか
    content: 発端から今回までの経緯
    relation: 時系列（各時点1情報）
    device: 日付付きリスト
    visual: false
  - id: b2
    question: 今どこにいるか
    content: 候補3社の比較
    relation: 比較（3対象 × 5軸）
    device: 表
    visual: true
  - id: b3
    question: 何で止まっているか
    content: 3つの未確認前提と、それぞれがブロックしているもの
    relation: 依存
    device: 図
    visual: true
    prose: |
      想定人数250名の定義が部署間でずれており、確定するまで3社の費用比較は成立しない。
      ブリッジ社のデータ保管場所は法務未確認で、確定するまで同社は候補として残せない。
      セキュリティ要件は法務と情報システム部で割れており、決着するまでアルファ社の可否が決まらない。
      つまり3つの前提がそれぞれ別の判断をブロックしている。
    prose_sentences: 4   # 3文以上なので図にしてよい

diagram_candidates:   # 3系統から最低3件。採用0でも残す
  - axis: 関係
    idea: 3つの未確認前提が、それぞれ何をブロックしているか
    prose_sentences: 4
    adopted: true
  - axis: 時間
    idea: 5月から今回までの経過と、判断目標がさらに先であること
    prose_sentences: 4
    adopted: true
  - axis: 量
    idea: 月額単価の対比（2,400円 / 1,100円 / 原文に記述なし）
    prose_sentences: 2
    adopted: false
    reason: 2文で書けるため却下。数値は表に残す

rhythm_check: 同一装置の2連続なし / 散文2連続なし
tier_a: 2/8 = 25%        # 下限20%
tier_ab: 5/8 = 62.5%     # 下限50%
read_area: NN%           # 上限60%。描画して測る
cell_over_30: N/NN = N%  # 表ごとに。10%超なら Tier B から外す
page_height: 1024px幅で NNNNpx（前回 3,209px）
```

`prose_sentences` が 2 以下の行は、`device: 図` にしてはいけない。
