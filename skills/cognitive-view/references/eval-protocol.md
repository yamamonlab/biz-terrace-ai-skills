## なぜこのファイルがあるか

`references/quality-rubric.md` が測るのは **成果物の性質**（情報保持率・表現変換率・7軸）であり、**読者が速く把握できたか** は一度も測っていない。しかし本 Skill の約束は把握速度そのものなので、中心の主張だけが未計測になる。

このファイルは、その1点だけを安く測る手順を定める。

**設問が易しいと全版が満点になり、何も分からない。** 実測で5版を同時に測ったところ 15/15 全問正答となり、版の優劣がつかなかった。合格条件を満たすことと、改善が効いたことは別である。弁別設問（3節）と探索コスト（4節）を必ず併用する。

## 1. VALIDATED と EVALUATED の境界

| 状態 | 満たしているもの |
|---|---|
| **VALIDATED** | `scripts/validate.mjs` が PASS し、`references/quality-rubric.md` の合格条件を満たす。**成果物の性質だけを確認した状態** |
| **EVALUATED** | 上に加えて、このファイルの理解到達テストを**2ジャンル以上**で実施し、合格条件を満たした状態 |

`CHANGELOG.md` と Release note には、どちらであるかを必ず書く。Behavior を変える変更（Visual Router、層の上限、モード境界、複雑度予算）では EVALUATED まで行う。文言整理や参照追加だけなら VALIDATED でよい。

## 2. 理解到達テスト（主プロトコル）

1回あたり15〜20分で終わる。

1. **入力を選ぶ。** `examples/sample-document.md` か、同等の長さ（2,000字以上）の実資料。機密を含まない
2. **設問を作る**（3節）。**入力を選んだ時点で書き、ファイルに保存してから変換に入る。** 出力を見てから作ると、出せた情報に合わせた設問になる。**実測でこの順序を破ったことがあり、その回の結果はバイアスありとして扱った**
3. **5秒層だけを見せる。** `<h1>` とメトリクスカードまで。構造層以降は隠す。回答者は別モデル、または原文を読んでいない人
4. 3問に回答させ、○/×を記録する（**回答時間も記録する**）
5. **構造層まで開いて見せる。** `<details>` は閉じたまま
6. 同じ3問に再度回答させ、○/×と時間を記録する
7. **原文を読ませて答え合わせ。** 誤答が「出力に情報が無い」のか「情報はあるが読み取れない」のかを区別して記録する

**手順7の区別が、このテストの本体。**

- 情報が無い → `quality-rubric.md` の情報保持率の問題。変換ではなく削減が起きている
- 情報はあるが読み取れない → **表現の問題**。表現変換率は満たしているのに速さが出ていない状態で、rubric では絶対に検出できない

## 3. 設問の作り方

Comprehension Brief の `comprehension_goal` を1問目にし、残り2問を次から作る。

| # | 問いの型 | 例 |
|---|---|---|
| 1 | **状態** — この資料は今どういう状態か（`comprehension_goal` そのまま） | 「この検討は今どの段階で、なぜ前に進んでいないか」 |
| 2 | **数値または制約** — 原文にある重要数値・期限・条件を1つ | 「予算の上限と、その根拠となる時点はいつか」 |
| 3 | **区別** — 確定事項と未確認事項の境界 | 「『定着率が高い』は計測値か、誰かの印象か」 |

**4問目に弁別設問を1問足す。** 「5秒層だけでは答えられないはずの問い」（構造層に初めて出る数値や関係）を混ぜ、**どの層で答えられるようになるか**を測る。これが無いと、易しい設問ばかりで全版が満点になり、版の優劣がつかない。

3問目は必ず**事実と推測の区別**を問う。ここが崩れると、読みやすくなった代わりに誤解を生んでいることになり、最も避けたい失敗になる。

数値のない入力では、2問目を「原文が明示していない前提を1つ挙げよ」に差し替える。

## 4. 合格条件

| 段階 | 条件 |
|---|---|
| **5秒層のみ** | 設問1に正答する |
| **構造層まで** | 設問1〜3すべてに正答する。**`<details>` を開かずに到達すること** |
| **全体** | 「情報はあるが読み取れない」型の誤答が0件 |

`<details>` を開かないと答えられない設問があった場合、その内容は**構造層へ引き上げる対象**であり、畳む判断が誤っている（SKILL.md「構造化できたものは畳まない」）。

回答時間は合否に使わない。人・モデル・環境で桁が変わるので、**同一条件での比較にだけ使う**。

### 探索コストを必ず記録する

正答率だけでは差がつかない（実測で5版すべてが15/15正答＝天井効果）。**差が出るのは探索コストのほう**なので、次を記録する。

| 指標 | 取り方 |
|---|---|
| 回答までの所要時間 | 同一条件での比較にのみ使う |
| **拡大・再読の回数** | 回答者がページの一部を拡大した回数、画像を読み直した回数 |
| 参照箇所の数 | 1問に答えるために何か所を突き合わせたか（回答者に申告させる） |

実測例: 同じ設問・同じ回答者モデルで、3,000〜3,500px の出力は**拡大なしで2回読めば答えられた**のに対し、6,977px の出力は**部分拡大を繰り返して12回のツール使用・2.2倍の所要時間**を要した。正答率は両方とも満点だった。**長さのコストは正答率には出ず、探索コストに出る。**

## 5. 比較実験（ルールを削る時）

`references/foundations.md` の「原理そのもの」に当たるルールを削る提案では、これを必須にする。

1. 同じ入力・同じ設問で、**ルールあり**と**ルールなし**の出力を2本作る
2. 回答者には、どちらがどちらか伏せて提示する（順序も入れ替える）
3. 段階ごとの正答数と回答時間を両方記録する
4. **正答数が落ちない、かつ時間が伸びない**場合にのみ、そのルールを削ってよい

1入力での1回の比較は証拠として弱い。最低2ジャンル・各1回は回す。

## 6. 報告フォーマット

```
入力: <ファイル名 / 字数 / ジャンル>
回答者: <モデル名またはロール>（原文未読）
設問: Q1 <状態> / Q2 <数値・制約> / Q3 <事実と推測の区別>

5秒層のみ:    Q1 ○  (NN 秒 / 拡大 N 回)
構造層まで:   Q1 ○  Q2 ○  Q3 ×  Q4(弁別) ○  (NN 秒 / 拡大 N 回)
参照箇所数:   Q1 = N か所 / Q2 = N か所 / Q3 = N か所
詳細層を開く必要があった設問: Q3
誤答の型: Q3 = 情報はあるが読み取れない（アラート枠の「鴇田の印象」が本文の数値カードと離れている）

判定: 不合格（構造層までで3問正答に届かず）
対応: 帰属の注記を該当数値の直下へ移す → 再測定
```

測定記録は利用側のrepositoryに残す（本 Skill には出力サンプルを置かない）。**どの commit の Skill で、どの入力を測ったかを必ず書く。**
